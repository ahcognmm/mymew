# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Always read `Architecture_Design.md` at the start of a session before making changes.** It is the source of truth for this project's design (comptime plugin registry, ReAct + Plan-and-Execute orchestration styles, self-healing loop, .jsonl memory, TUI/thread model). Code should conform to it; if a change requires deviating from it, update the doc in the same change.

## Commands

- Build: `zig build`
- Run interactively (TUI): `zig build run` (Ctrl+P toggles the orchestration style shown in the status line; see Architecture below)
- Run headless (one-shot): `zig build run -- -p "<prompt>"` (add `-s <session-id>` to scope memory to `mymew_session_<id>.jsonl` instead of the default `mymew_memory.jsonl`; add `-m react|plan-execute` to pick the orchestration style, default `react`)
- Run all tests: `zig build test`
- Run a single test: tests live inline in the relevant `src/**/*.zig` file (e.g. `src/core/engine.zig`, `src/core/plan.zig`) using `test "..."` blocks and `std.testing`; there is no per-file test runner target, so filter by editing/temporarily isolating the test or running `zig build test` and reading output for the named test. **Gotcha:** Zig 0.16's `zig test` only registers a file's `test` blocks once that file's container is fully resolved, which merely calling one of its functions does not force — `src/main.zig` has a `test { std.testing.refAllDecls(...) }` block that exists solely to seed this; a new file with its own `test` blocks needs a line added there or `zig build test` will silently report success having run zero of its tests.
- Zig toolchain: `minimum_zig_version = 0.16.0` (build.zig.zon); installed `zig version` is 0.16.0.

### Environment / running the agent

The GLM provider (`src/core/llm.zig`) requires `GLM_API_KEY` or `ZAI_API_KEY` (z.ai / Zhipu GLM). Optional: `GLM_MODEL`, `GLM_BASE_URL`, `MYMEW_MEMORY_PATH`.

## Architecture

This is a Zig CLI/TUI AI agent using **comptime duck-typed plugins** instead of vtables/dynamic dispatch — see `Architecture_Design.md` §2 for the rationale. Concretely:

- `src/main.zig` wires the concrete instantiation: `Tools` is a tuple of tool plugin modules, `Hooks` is a tuple of interceptor hook modules, `Agent = agent_mod.Agent(Tools, llm.Glm, Hooks)`. To add a tool, write a new module in `src/plugins/tools/` matching the contract in `src/core/tool.zig`, then add it to the `Tools` tuple in `main.zig`; same for hooks with `src/plugins/hooks/` / `src/core/hook.zig` / the `Hooks` tuple. To add an LLM provider, write a type exposing `chat(self, gpa, io, messages, tools, token_writer: ?*Io.Writer) anyerror!Message` (see `src/core/llm.zig`'s `Glm` and `Mock`) and swap it into the `Agent(...)` instantiation.
- **Tool contract** (`src/core/tool.zig`): a tool module exposes `Args` (a struct — reflected at comptime into the JSON schema sent to the LLM), `name()`, `description()`, and `execute(alloc, args: Args) anyerror![]const u8`. `tool.invoke` never returns a Zig error to the caller — parse failures and execution failures both become an `InvokeResult` (`.ok` / `.invalid_args`) that the orchestrator can feed back to the LLM. A tool may also implement an *optional* `describe(alloc, args: Args) anyerror![]const u8` (`tool.describeArgs` calls it if present, comptime-dispatched the same way `execute` is) — a short, human-readable one-liner for the TUI's tool-call status marker (design doc §3.6), e.g. `read_file` → `"Reading file {path}"`. Tools without `describe` fall back to a truncated dump of the raw args JSON.
- **`core/engine.zig`** is the orchestrator (`Engine(Tools, Provider, Hooks)`), supporting two runtime-selectable styles via `Style` (`.react` / `.plan_execute`, set with `setStyle()`, default `.react`). `step()` is a thin dispatcher over `stepReact`/`stepPlanExecute`, both of which delegate the actual provider-call/tool-dispatch/self-healing cycle to a shared `runToolLoop(turn_start, writer, base_view)`: calls the provider with `base_view` (**not** always `self.mem.items()` — see below), and if it returns tool calls, dispatches each via a compile-time-unrolled `inline for` over `Tools` (static routing, no runtime vtable), appends results as `role: .tool` messages, and loops. Malformed tool args trigger the self-healing loop: feed the diagnostic back to the LLM, retry up to `max_retries` (3), and on exhaustion `escalate()` — prune the failed turn out of memory down to a single system note and return an `.escalated` report (design doc §3.2–3.3). `stepPlanExecute` (design doc §3.5) additionally runs `buildPlan()` — an ephemeral, never-persisted planning exchange (`src/core/plan.zig` for the `Plan`/`PlanStep` types) that gracefully degrades to a single-step plan rather than escalating if the LLM never returns parseable plan JSON — then calls `runToolLoop` once per step plus once more for a final synthesis answer, all sharing one `turn_start` so an escalation anywhere prunes the whole turn. **Important:** every step's `runToolLoop` call is given a *curated* `base_view` (prior conversation + plan + one-line summaries of completed steps, not their raw tool-call transcripts) rather than the full `self.mem.items()` — this is deliberate (see design doc §3.5 point 5): sending a step the full growing history caused it to imitate its own prior chatty replies instead of following instructions. Only the synthesis call passes `self.mem.items()` (full history) as `base_view`. Everything is still persisted to `self.mem`/`.jsonl` regardless of what's sent to the provider — curation only affects what the model *sees*, never what's recorded.
- **Hook contract** (`src/core/hook.zig`, design doc §3.7/§8, full spec in `docs/feat/hooks.MD`): a second plugin category — interceptor hooks that observe, mutate, or veto orchestration steps. Unlike the tool contract, this one is **sparse**: only `name()` is mandatory; the seven methods (`onTurnStart`, `preLlm`, `postLlm`, `preTool`, `postTool`, `onEscalate`, `onTurnEnd`) are each optional, checked at their `engine.zig` call sites via `@hasDecl`. `Engine`/`Agent` take the `Hooks` tuple as a required third comptime parameter (`.{}` for none). Hooks fire in tuple order, mutations chain, the first `preTool` veto short-circuits (veto = red status dot, flows back as the tool result, does *not* count as a self-healing retry), `postTool` never sees `.invalid_args` diagnostics, `postLlm` is content-only (never `tool_calls`) and skipped during `buildPlan`. Ownership rule: hooks allocate replacements from `Ctx.scratch` (engine-owned arena) and free nothing; the engine normalizes back to gpa/arena ownership at each boundary. Sample hook: `src/plugins/hooks/tool_audit_log.zig`.
- **`core/memory.zig`** is the append-only `.jsonl` store: `hydrate()` reads it line-by-line into an in-memory arena on `init`, `append()` writes one new line without touching existing content, and `prune()` (called only from escalation) clears and rewrites the whole file to match the pruned in-memory context.
- **`core/agent.zig`** owns the background-thread lifecycle: `Agent(Tools, Provider, Hooks).spawn()` (hooks tuple forwarded untouched to the inner `Engine`) runs the `Engine` on a detached thread; the render thread calls `submit()`/`requestStop()` and drains streamed output via `core/io_bus.zig`'s `Channel` (thread-safe byte queue) and `ChannelWriter` (an `Io.Writer` that pushes to the channel and pings a wakeup fd/pipe so a `poll()`-based frontend notices immediately). This split (main thread = TUI/render, background thread = orchestrator) is design doc §5.2. `Agent.eng.style` is a `std.atomic.Value(Style)` specifically so the render thread can call `agent.eng.setStyle(...)` directly (e.g. on the Ctrl+P toggle) without a data race.
- **`src/main.zig`** also supports a headless path (`-p`/`--prompt`) that runs the same `Engine.step()` synchronously and prints to stdout — no threads, no raw terminal mode — for scripted/piped use instead of only through the TUI.
- **`src/tui/app.zig`** is the TUI frontend (raw terminal mode, layout/rendering, key handling); it is a consumer of `io_bus` and has no orchestrator logic of its own — it tracks only a plain `plan_execute: bool` (set via `setStyle()`) to render the `[react]`/`[plan]` status-line tag, not `core.engine.Style` itself, keeping `app.zig` free of any `core/*` dependency. It also renders the tool-call status dot (design doc §3.6): `wrapLogicalLine`'s existing SGR-sequence scan (already used to track the "thinking" reasoning-span gutter) additionally recognizes the tool-pending/-done marker bytes `core/engine.zig` writes, recording the pending dot's byte offset in `self.transcript` and overwriting it *in place* (never re-emitting the line) once a done-signal patches it to green/red; `tickDots` (the same ~400ms timer already driving the "thinking..." animation) blinks a pending dot by toggling those same bytes between bright/dim yellow. As with `thinking_start_sgr`, the marker byte sequences are duplicated as matching literals in both `core/engine.zig` and `tui/app.zig` rather than shared via an import, to keep `app.zig` free of any `core/*` dependency.
